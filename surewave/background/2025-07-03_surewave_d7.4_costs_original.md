## Why cells break outside Google Sheets

1. Google wrapper. Formulas Excel has no equivalent for are saved as `=IFERROR(__xludf.DUMMYFUNCTION("<formula>"), <last result>)`. Google Sheets reads the formula inside; Excel and LibreOffice see an unknown function and show the last result Google computed, frozen. Cells filled by such a formula's spill are saved as `__xludf.DUMMYFUNCTION("COMPUTED_VALUE")` with their value.
2. Missing prefixes. In an xlsx file, functions newer than Excel 2010 must be stored with a prefix (`_xlfn.SEQUENCE`, `_xlfn.MAP`, `_xlpm.` for LAMBDA parameters). Google Sheets saved them without the prefix, so Excel and LibreOffice read `SEQUENCE`, `UNIQUE`, `MAP`, `LAMBDA`, `SCAN` and `MINIFS` as unknown names (`#NAME?`).

The other 1,687 of the 1,895 formulas are ordinary (208 cells are affected) and work in any spreadsheet program, among them the anchoring cost (`out_loc` row 20).

## Decision (2026-11-23)

D7.4 version 2.0 with the cost model v3 is delivered and used by the coordinator. Its figures are the reference for SUREWAVE documents. The v4 model planned in T157 is not made, and the verification items listed under "Not done" below will not be pursued. The errors found in the original that v3 does not correct (anchoring per ring instead of per pile and chain; pontoon-connection maintenance counted once a year; no fabrication labour) remain known limitations of the delivered model.

## State of verification (2026-11-23)

### Established

1. The original is the Drive file unchanged. Downloaded with the Drive API on 2026-11-23; size and MD5 equal the values Drive reports for the file.
2. The original contains every formula, including the 208 that only Google Sheets reads (listed above). None is missing from the file. Google Sheets reads them from this file, since the model is stored as xlsx and not as a native Google Sheet.
3. The original and the Zenodo copy hold the same stored results. Compared cell by cell on 2026-11-23 with a one-off script: no cell differs, apart from cells that are empty in the original and 0 in the copy (the spill areas in `pontoons`, `summary!A1`).
4. The original and the Zenodo copy hold the same formulas, by the same comparison:
   - 195 formulas are identical once Excel's prefixes (`_xlfn.` etc.), Google's wrappers, spaces and letter case are disregarded;
   - 6 formulas (`pontoons!Q3`, `T3`–`T6`, `T16`) are written differently: the original lists the `FILTER` conditions as separate arguments (Google form), the copy multiplies them (Excel form). Read and judged to mean the same; the original's stored results of these cells match the reference model (point 6), the copy's form has not been recalculated;
   - 7 cells (`pontoons!Q4:Q6`, `R3:R6`) are spill placeholders in the original and plain values in the copy;
   - `AA4` and `AA5` are wrapped in both files (`__xludf.DUMMYFUNCTION` in the original, `__xludf.UNSUPPORTED` in the copy) around the same formula and the same frozen result.
5. In T157 (2026-11-20), done on the Zenodo copy, not on the original:
   - the Python reference model (`scripts/d74_cost_model.py`, function `v2_outputs`) reproduces all 27 × 31 `out_loc` results stored in the Zenodo copy (`scripts/test_d74_cost_model.py`);
   - v3 was built from the Zenodo copy's input sheets, with every calculation rewritten in plain Excel formulas and the corrections listed in `surewave/deliverables/2026-11-20_surewave_d7.4_costs_v3_changelog.md`; v3's results match the corrected Python model (`v3_outputs`).

6. Check A (2026-11-23), run on the original: the Python reference model (`v2_outputs`), with the original's own inputs, reproduces every `out_loc` result stored in the original, 837 of 837 cells (27 cases × 31 rows, tolerance 1e-9 relative). This includes the 189 cells with Google-only formulas (rows 24, 25, 27–29, 33, 34). The Google-only cells in `pontoons` also match the model: cheapest cost per pontoon type (`S3:S6`), cheapest design (`P3:P6`), pontoon counts (`T3:T6`, so the six `FILTER` formulas of point 4 give the model's values), the totals `AA4` and `AA5` (including the count error), the 20 design × size × type combinations (`L3`) and the five designs (`M69`). The reference model is therefore a faithful copy of the delivered model, Google-only formulas included.
7. Check B (2026-11-23), run on the original: the v3 model (`v3_outputs`) with all nine documented corrections switched off does not reproduce the original. 203 of the 837 cells differ, in eight rows (production, reinstallation cost, LCOE, revenue, NPV, ROI, IRR, payback). Each difference was traced and confirmed by calculation to one of four changes that v3 makes and that its correction switches do not undo:

| # | In the original | In v3 | Confirmed | In the T157 changelog |
|---|---|---|---|---|
| a | Second-life terms (rows 27–29) carry an extra factor (1 − r) | Factor dropped | Reinstallation cost and O&M: v3 = original ÷ (1 − r) in 27 of 27 cases; production in the 9 base cases | Yes, item 3, but the model drops the factor also with the discounting correction off |
| b | Pessimistic and optimistic columns: second-life production with the base rate and lifetime (optimistic), base cooling in some rows (pessimistic) | Each variant uses its own inputs | Remaining production difference −0.30 % in all pessimistic and +0.11 % in all optimistic cases | Yes, item 9, but the variant correction switch restores only the `inter_gen` part |
| c | IRR and payback cash flows apply module degradation to O&M as well as to production (`(price × production − O&M) × (1 − degradation × t)`) | O&M not degraded | Rebuilding the original's IRR with O&M not degraded gives v3's value exactly (n_2, b_10, m_10); effect −0.01 to −0.08 percentage points (m_10: 10.828 % → 10.821 %) | No |
| d | Payback counted as the year number t + 1 in which cumulative net cash reaches CAPEX | Year index t in which cumulative net cash, CAPEX included, reaches zero | v3 one year shorter in all 14 cells with a payback (m_10: 8 → 7) | No; the changelog says payback is "as in v2" |

   Consequence: the statement "v3 differs from the original only by the documented corrections" does not hold. Differences a and b are documented as corrections but cannot be switched off one by one in the model; c and d are not documented. c is a correction (O&M does not degrade with the modules); d is a change of counting convention that makes every v3 payback one year shorter than the original's convention would give.

### Not done

1. Changes c and d are not yet in the T157 changelog, and the model has no switches that reproduce a and b fully. Until then, the leave-one-out effects in the changelog do not add up exactly to the difference between the original and v3.
2. The behaviour of the file in Excel and LibreOffice is described from how the file is written, not observed.
3. Apps Script: scripts and named functions are not stored in an xlsx file. A check in the file in Google Sheets (Extensions → Apps Script) settles whether there are any.

Checks A and B were run with a one-off script (session scratchpad, not stored in the repo), using `scripts/d74_cost_model.py` unchanged.
