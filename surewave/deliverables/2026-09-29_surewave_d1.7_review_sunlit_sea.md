# SUREWAVE D1.7 — Sunlit Sea review

## 1. D8.4 (Exploitation Pathways & Definitive Business Plan) is absent from Table 1

Table 1 (data inventory by WP) does not reference D8.4 anywhere. D8.4 is the definitive exploitation deliverable — Sunlit-Sea led, restricted dissemination, M36 due — and generates a substantial body of data: Key Exploitable Result (KER) analyses, IPR mapping, per-partner exploitation plans, market analyses, value proposition materials, and business models with financial projections. All of that data has access classifications, retention rules, and IPR conditions that the DMP needs to inventory.

Currently the exploitation-related row (row on "Business cases, market studies, exploitation assessments and commercial planning information") maps to WP7+WP8 with associated deliverables "D7.4; D8.1; D8.5" — which does not include D8.4.

**Proposed fix.** Add a dedicated row (or extend the existing exploitation row) that names D8.4 explicitly, notes its restricted dissemination level per the DoA, identifies Sunlit Sea as data owner and coordinator-approved data classifier, and states the retention arrangements for confidential per-partner exploitation input.

## 2. Duplicate Zenodo record ID in Table 2 — D3.4 and D6.2 both listed as 22660916

Table 2 (Public SUREWAVE outputs deposited in Zenodo) shows:

- D3.4 "SUREWAVE FPV System Design (D3.4 Summary of Global System Design)" — Zenodo Record ID 22660916 — 2024-05-31 — Open.
- D6.2 "SUREWAVE Basin Test Results (D6.2)" — Zenodo Record ID 22660916 — 2025-03-10 — Open.

The same Zenodo record ID cannot correspond to two different deliverables. One of the two entries is a copy-paste error. Given the different publication dates and WPs, the safer assumption is that one deliverable has been assigned the wrong ID and the actual DOI does not resolve as claimed for one of them.

**Proposed fix.** Verify the correct Zenodo record IDs for both D3.4 and D6.2 from the SUREWAVE Zenodo Community (`zenodo.org/communities/surewave/`), and correct whichever entry is wrong. Recommend running the full Table 2 through a resolver check as a sanity pass before final submission — the same copy-paste risk applies to every ID.

The four candidates above are cross-checked against the SUREWAVE communication and publications log maintained on the consortium SharePoint: [`communication_log.xlsx`](https://sintef.sharepoint.com/:x:/r/teams/work-22638/_layouts/15/Doc.aspx?sourcedoc=%7BD437CAFA-DBD0-4C07-95E1-02F3B67E72E1%7D&file=communication_log.xlsx). If they are pending deposit at the DMP reporting date, that should be stated explicitly — either by adding rows with "pending publication" in the Access column, or by adding a note under the table explaining the cut-off date.

**Proposed fix.** State the reporting cut-off date explicitly in the paragraph before Table 2, and either add the missing entries with correct IDs or add a short "pending deposit" list below the table so external readers can distinguish "not delivered" from "delivered but not yet on Zenodo". Recommend reconciling the full Table 2 against the `communication_log.xlsx` tracker linked above before submission.
